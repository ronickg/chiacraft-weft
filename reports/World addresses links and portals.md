# Key every world, co-sign every link

The prior art supports the Phase 3 plan's shape and points to one concrete design for slices 2–5. **Give each world its own Ed25519 key, derived from the account words on a hardened path and vouched for by the account. That key's public half is both the world's address and its iroh `EndpointId`.** Each hosted world runs its own endpoint, and the player always joins other worlds through the account endpoint. **A link is one labelled record that both world keys sign over identical bytes.** It is modelled on Matrix's co-signed federation invite and ActivityPub's Follow/Accept. It names worlds, never coordinates, and either side can end it with an irreversible tombstone, as UCAN revocations work. **Portals are built-in blocks that point at a link id.** **Travel follows the Second Life/OpenSimulator pattern of preparing first and releasing afterwards.** As the player walks toward a portal, the game resolves the destination, asks it for admission with a short-lived ticket signed by the origin world, and downloads packages after consent. Only once the destination confirms arrival does the origin let go of the player. The plan needs five changes. Requests have to reach the owner's game even when the world isn't open, because worlds are offline most of the time. Joins should go back to the account endpoint. Portal blocks must ship in chiacraft's own built-in mod, not in a package. Binding a portal needs an owner check before Phase 7's operators exist. "Defaults open" should mean worlds *receive* requests and visitors by default but never *auto-accept* strangers. Citations mark sourced facts. Statements tagged *(inference)* are this report's synthesis. Two points have no precedent to cite: no shipped game uses public-key travel tickets, and no standard defines a link that two parties co-sign and either can revoke alone.

## A world key becomes the address, and the account vouches for it (slice 2)

### What iroh gives for free, and what it forbids

In iroh 1.x (1.4.1 on docs.rs), **an `EndpointId` is simply an Ed25519 `PublicKey`, each endpoint has exactly one `SecretKey`, and dialing by id alone works only when an address-lookup service is configured** ([docs.rs/iroh](https://docs.rs/iroh/latest/iroh/)). The 1.x name for discovery is `address_lookup`. Lookup services stack: several `.address_lookup(...)` calls are queried concurrently, and `MemoryLookup` lets the app seed addresses it already knows ([iroh 1.0.0 address_lookup.rs](https://docs.rs/crate/iroh/1.0.0/source/src/address_lookup.rs)). By default the pkarr publisher **republishes every 5 minutes and publishes only the home relay URL, not IP addresses**. That default exists to avoid "leaking IP addresses to the public pkarr server" ([iroh pkarr.rs](https://docs.rs/crate/iroh/1.0.0/source/src/address_lookup/pkarr.rs)). The default resolver is n0's dns.iroh.link, which the docs call "a more central service". A Mainline DHT lookup ships separately as `iroh-mainline-address-lookup` 0.6.1, built for iroh ^1.0 ([docs.rs iroh-mainline-address-lookup](https://docs.rs/iroh-mainline-address-lookup/latest/iroh_mainline_address_lookup/)).

The hard constraint is on the relay: **when a second endpoint connects with the same id, the relay sends `SameEndpointIdConnected` to the older one, which then receives "no more messages"** ([iroh-relay protos](https://docs.rs/crate/iroh-relay/0.98.0/source/src/protos/relay.rs)). Slice 1 already ran into this. A per-world key turns the constraint into a design rule *(inference)*. Each hosted world runs its own `Endpoint` with the world key. The game keeps one account endpoint with the login key for joining other worlds and for account-level protocols. A world key must never be live in two places at once.

This changes slice 1's workaround. Today, joining while hosting goes out through the hosting endpoint because both endpoints shared the login key. **Once the world has its own key, the account endpoint and the world endpoint no longer collide, so joins should go back to the account endpoint.** That keeps the guest's identity, its remote endpoint id, equal to the player's login key, which protocol 4 already authenticates *(inference)*. A player who hosts one world and visits another runs two endpoints. A headless server with N worlds runs N+1. Each costs one relay connection and one republish every five minutes. The notes found no official guidance on many endpoints in one process, so measure this before relying on it.

### Derivation, certification and rotation

SLIP-0010 permits only **hardened** derivation for Ed25519 ([SLIP-0010](https://github.com/bcndev/slips/blob/master/slip-0010.md)). A hardened child key reveals nothing about the words, so a headless server can hold a world key without the account. The recommended derivation uses the same mechanism as the login and content keys: `world_key = derive(words, label "world", index', generation')` *(inference)*. **The index should be a random 31-bit number chosen when the world is created and saved in the world**, not a counter. Otherwise one account that creates "world 0" on two machines gets the same key twice, and the relay drops one of them. "Duplicate world" must likewise draw a new index. The generation starts at 0 and exists only so that a leaked world key can be replaced.

Every system surveyed makes **the public key the name, so changing the key changes the address**. Tor v3 addresses encode the long-term identity key ([Tor rend-spec](https://spec.torproject.org/rend-spec/protocol-overview.html)). IPNS names hash the public key and have no rotation mechanism ([IPNS spec](https://specs.ipfs.tech/ipns/ipns-record/)). pkarr does not address rotation at all ([pkarr](https://github.com/pubky/pkarr)). The systems that keep a stable name across rotation add one level of indirection. Tor keeps its identity key offline and signs short-lived online keys with it. A W3C DID stays fixed while its verification methods change ([DID Core](https://www.w3.org/TR/did-1.0/)). chiacraft already has that higher key: the account identity key, which vouches for content keys in `package.sig`. The plan's "World DID" will take the same role later.

The design is therefore a **world certificate**. It is a labelled text in the style of `chiacraft package v1`, signed by the account: `chiacraft world v1 / world: <key> / owner: <account key> / generation: <n> / created: <time>` *(inference)*. The world serves it to anyone who asks, and links and saved entries keep a copy. Rotation draws a new generation, and the account signs `chiacraft world-moved v1 / from / to`. The account signs the move, not the old world key, so a thief holding the old world key cannot redirect the world. Clients find the move notice at the owner's account endpoint (next section). In Phase 4 the world DID's record of the current key replaces both the certificate and the move notice; the plan's "Finding worlds" already proposes exactly that. A separate long-lived "name key" that publishes a pkarr pointer to the current key would also work, but it adds a lookup to every join and duplicates what the DID will do. **Keep "address = world key" and treat rotation as rare.**

### Discovery stack, address format and the saved-worlds list

To satisfy rule 1 (no single hard dependency), **publish and resolve through n0 DNS/pkarr and the Mainline DHT together, with mDNS for LAN and `MemoryLookup` seeded from saved entries and link hints** *(inference)*. Make the pkarr relay and DNS origin settings, as relays already are. Keep `AddrFilter::relay_only()` as the default. DHT records stay ephemeral: BEP 44 items "MAY expire in 2 hours" and should be re-announced hourly ([BEP 44](https://bittorrent.org/beps/bep_0044.html)). pkarr packets are capped at 1000 bytes ("for discovery, not storage") ([pkarr](https://github.com/pubky/pkarr)). So records hold only reachability, never status or lists.

Zooko's triangle rules out raw keys that are also readable. The petname literature's advice is to show a local nickname over the key, render self-chosen names distinctly so they cannot pose as petnames, and share by QR or link because typing a key is "far more dangerous" ([Petnames paper](https://files.spritely.institute/papers/petnames.html)). The address should be `chiacraft://w/<world key>` with optional hints `?n=<proposed name>&r=<relay>&a=<ip:port,...>&i=<invite token>` *(inference)*. The key alone must be enough. The existing `endpoint-id;relay-url;ip:port,...` ticket stays accepted as the hint-carrying form.

The local **Worlds** list keeps one entry per world:

| Field | Purpose |
|---|---|
| world key | the address |
| petname | the player's own name for it |
| proposed name | shown distinctly, with a fingerprint or identicon |
| via | who shared it, e.g. "via Alice" |
| owner account key and world certificate | ownership, and where to look after a rotation |
| last relay and addresses | seed for `MemoryLookup` |
| last seen and last status | shown in the list |
| trust flags | blocked, always relay, ask before download |

**Friends' worlds** come from a friend's account endpoint rather than any directory *(inference)*. A friend is a saved account key with a petname. When the Friends screen opens, the game dials each friend on an account ALPN `chiacraft/worlds/1`. The friend's game returns an account-signed list of the worlds they own (current keys, which are open now, an optional favourites list). The petname paper calls these "edge names". The same endpoint answers "where did world X move?". Steam's "Join Game" works by publishing a `connect` string in rich presence ([Heathen KB](https://kb.heathen.group/steam/multiplayer/rich-presence)). The pull above reproduces it without Steam. Push presence through iroh-gossip can come later.

### Knowing a world is online

No global "online" bit exists. Records are cached aggressively and **any DHT node can re-announce a signed record without the private key**, so a record's presence does not prove the publisher is running ([BEP 44](https://bittorrent.org/beps/bep_0044.html); [pkarr](https://github.com/pubky/pkarr)). Minecraft's answer, pinging every saved server directly on opening the list for MOTD, players and version ([wiki.vg SLP](https://wiki.vg/Server_List_Ping)), carries over unchanged. **Each world endpoint should serve a small `chiacraft/status/1` ALPN** returning the proposed name, world certificate, protocol range, lock hash and total package size, players and capacity, join policy (open / via links / closed), and whether it takes link requests *(inference)*. The Worlds screen dials every entry in parallel with a short timeout. A resolved record whose `last_updated` is stale skips the dial. The status ping also guards against hosting a world twice: before hosting, the game dials its own world key, and an answer means "this world is already open elsewhere". Nobody has published how long dns.iroh.link keeps a record after its last publish, so "last seen" must come from the game's own pings.

## Links copy Matrix's co-signed invite, not a delegation chain (slice 3)

### The request–accept shape every federation converged on

**ActivityPub's Follow is a request: the sender adds the target to `following` only after an `Accept`, the receiver MAY omit `Reject` "to protect privacy", and `Block` is never delivered to the blocked actor** ([ActivityPub](https://www.w3.org/TR/activitypub/)). **In Matrix, an invite to another server must be "signed by both the inviting homeserver and the invited homeserver"**. The invited server adds its signature and "all other fields … should remain untouched". It can refuse with `M_FORBIDDEN` or, since v1.18, `M_INVITE_BLOCKED` ([Matrix S2S API](https://spec.matrix.org/latest/server-server-api/)). That co-signed invite is the closest existing analogue to a link signed by both worlds. A Biscuit or UCAN chain is built for delegating authority through several hands, which is more machinery than a symmetric, human-approved, two-party record needs ([Biscuit spec](https://doc.biscuitsec.org/reference/specifications)).

**The link record.** It is a labelled text in the same fixed-order, hex-field style as `package.sig`, which is canonical by construction and sidesteps the canonical-JSON trouble SSB and Matrix had to specify around ([SSB guide](https://ssbc.github.io/scuttlebutt-protocol-guide/); [Matrix appendices](https://spec.matrix.org/latest/appendices/)). The fields are `chiacraft link v1 / a: <lower world key> / b: <higher world key> / requested-by / created / expires (optional) / nonce / terms` *(inference)*. The two signatures sit outside the signed bytes, each with a key id so world DIDs and rotated keys fit later, as Matrix does with `ed25519:<id>`. **The link id is the BLAKE3 hash of the signed text, so both copies share an id, and the accepted record is exactly the request plus a second signature.** Bugs where someone accepts something different from what was asked cannot occur. The record never contains portal positions; those stay world-local (next section). Verify over the bytes received and never re-encode. The purpose label works like SSHSIG's namespace: it stops a world key's link signature from being replayed as any other signature ([PROTOCOL.sshsig](https://raw.githubusercontent.com/openssh/openssh-portable/master/PROTOCOL.sshsig)).

**Messages on `chiacraft/link/1`:**

| Message | Contents |
|---|---|
| Request | the link text signed by A, A's world certificate, an optional invite token, a note of at most a few hundred characters |
| Accept | B's signature over the identical text |
| Decline | optional; the default is silence |
| Revoke | below |

Requests expire on the requester's side after about 14 days. A newer request replaces an older one for the same pair. A world keeps at most about 100 pending requests and evicts the oldest. All of these numbers are *(inference)*; no source gave limits.

### Offline delivery is the real problem, and the plan understates it

Every system that delivers to an offline peer uses an always-on helper chosen by the recipient. **Nostr's NIP-17 says clients "MUST only publish" DMs to the relays in the recipient's kind 10050 list, and with no list "the user is not ready to receive messages and clients shouldn't try"** ([NIP-17](https://github.com/nostr-protocol/nips/blob/master/17.md)). Briar Mailbox stores messages on a spare always-on device and relays only between the owner and existing contacts ([Briar Mailbox](https://briarproject.org/news/2023-briar-mailbox-released/)). Holepunch's blind peers store data they cannot read ([blind-peer](https://github.com/holepunchto/blind-peer)). Without a helper, ActivityPub and Matrix fall back to sender-side retry ([Matrix S2S API](https://spec.matrix.org/latest/server-server-api/)).

A chiacraft world is online only while its owner plays it or a headless server runs it, so two owners' windows rarely overlap. The design therefore delivers in three layers *(inference)*. First, **an outbox with retry**: the requester's game keeps the request and retries whenever it runs, with backoff. Second, **the owner's game as the inbox**. Requests go first to the world key, then to the owner's account endpoint named in the world certificate. The game answers `chiacraft/link/1` on the account endpoint for every world it owns, on any screen, files the request into that world's inbox, and lets the owner accept from the title screen. That works because the world key can be derived from the words without loading the world. Accepts and revocations travel back the same way. Third, later, **recipient-chosen mailboxes**: the status reply and the worlds list carry an `inboxes` field, Nostr-10050 style. It holds a friend's headless server or a community relay that keeps size-capped, encrypted blobs and releases them only to the authenticated owner. Define the field now and ship it empty, then implement mailboxes alongside Phase 7's headless servers. A DHT slot does not work as an inbox. BEP 44 items are written under the writer's own key, so the recipient cannot find requests from strangers it doesn't know.

### Pre-allow, invite tokens and revocation

Pre-allow is a per-world policy:

| Mode | Behaviour |
|---|---|
| open (default) | requests land in the inbox |
| allowlist | listed world keys or owner account keys (later DIDs) are countersigned automatically |
| invite token | auto-accepted |
| closed | requests are dropped silently |

Tokens are the capability idea proposed after Matrix's August 2025 invite-spam wave. **A per-recipient token both addresses the recipient and grants the right to send, and the token a spammer uses reveals who leaked it** ([Frederickson, Aug 2025](https://www.terracrypt.net/posts/matrix-spam.html)). The design for chiacraft *(inference)*: a token is 16 random bytes stored with an expiry and a use count, and it rides in the `i=` hint of a shared address link.

**Revocation should copy UCAN.** In UCAN a revocation is a signed message naming the content hash of what it revokes, it is "immutable and irreversible", it is accepted even when it arrives before its target, and the party controlling the resource must cache it. Expiry "SHOULD be the preferred method" and revocation "the last line of defense" ([UCAN Revocation](https://github.com/ucan-wg/revocation)). Let's Encrypt reached the same verdict for the WebPKI: "revocation doesn't work very well", hence six-day certificates ([Let's Encrypt](https://letsencrypt.org/2025/02/20/first-short-lived-cert-issued/)). For chiacraft *(inference)*: either world signs `chiacraft link-revoke v1 / link: <id> / at`. The revoking world stops honouring the link at once, and the outbox delivers the tombstone. The tombstone is also the answer the next time the other world presents the link. Relinking requires a new request with a new nonce, which gives a new id. **Short-lived links are unnecessary**, because traversal is always live: the destination checks its own link store and tombstones at admission, so a stale copy on the other side fails safely. The worst case is a dangling portal on the side that hasn't heard yet. Both worlds keep links, tombstones, inbox and outbox in the world save, so they move with the world to a headless server.

## Portals point at a link id, and travel prepares before it commits (slices 4 and 5)

### Portal blocks: built in, owner-bound, coordinates kept local

Hypergrid addresses take the form `hop://host:port/region/x/y`, and a missing region falls back to the destination's default region ([OpenSim Hypergrid](http://opensimulator.org/wiki/Hypergrid)). Second Life parcel owners pick Blocked, Landing Point or Anywhere for teleport arrivals ([SL wiki](https://wiki.secondlife.com/wiki/Viewerhelp:About_Land_-_Options)). In both, **the destination owner decides where arrivals land**. chiacraft should follow suit *(inference)*. A portal block's block entity stores only a link id. Each world places its own portal for a link, and that portal is both departure and arrival point; v1 allows one per link per world, so placing a second moves the binding. The destination's position is sent at admission time, so owners can move portals without re-signing anything.

Two practical points follow *(inference)*. **First, the portal block must live in chiacraft's built-in mod, not in a package.** Package-based worlds pin different package sets, and the portal has to exist in every main-universe world and in every save, whatever was swapped in. **Second, binding a portal to a link must check that the actor is the world owner**, the account named in the world certificate, or the world itself on a headless server. Today any player can `/give`, so slice 4 needs this minimal permission check ahead of Phase 7's operators.

The portal has four visible states: unbound, ready, destination offline, and link closed. It shows the destination's petname or proposed name with a fingerprint, whether both sides accepted, players online, the download still needed, and whether the connection would be relayed or direct. VRChat's portal preview shows world, dropper, instance type, capacity and a 30-second timer ([VRChat wiki: Portals](https://wiki.vrchat.com/wiki/Portals)). Slice 4 can ship walking in with an ordinary blocking join behind a transition screen. Slice 5 then moves the work ahead of the step.

### Preparing ahead: child agents, not seamless meshing

**Second Life keeps "child agents" in neighbouring regions so the viewer can "see into" them, and a crossing promotes the child to root** ([sldev, 2008](https://list-archives.secondlife.com/sldev/2008-September/011904.html)). OpenSimulator's `ISimulationService.CreateAgent` asks the destination to create the agent *before* the move. A release message goes "from the receiving region back to the departing region to say the client has made contact", and only then does the origin close its copy ([ISimulationService.cs](https://sledjhamr.org/cgit/opensim-SC_OLD/plain/OpenSim/Services/Interfaces/ISimulationService.cs)). Seamless designs such as Star Citizen's jump tunnels and Photon's overlap zones transfer authority over shared entities ([Server Meshing Q&A](https://api.star-citizen.wiki/comm-links/18397); [Photon](https://blog.photonengine.com/building-a-seamless-mmo-backend-across-machines/)). chiacraft's worlds are unrelated maps, so a **discrete jump behind a short themed transition** (EVE's model) fits better than meshing. The ghost-connection idea still applies to the approach.

As the player approaches, the game works in three zones (radii illustrative; no source published prefetch distances) *(inference)*:

| Zone | Action |
|---|---|
| Outer, about 32 blocks | resolve the destination, ping status, open the account endpoint's QUIC connection |
| Middle, about 16 blocks | send an admission query with the travel ticket and get a reservation plus the package offer; show the existing consent sheet as an in-world prompt; download in the background into the BLAKE3 store |
| Portal face | commit |

Only the nearest portal is prepared. Walking away cancels with hysteresis, the same reason Second Life triggers crossings "one meter past the boundary" ([SL Wiki: Region crossing](https://wiki.secondlife.com/wiki/Region_crossing)). If the download is still running at the portal face, the transition screen shows progress and a Cancel button. Nothing has committed yet, so Cancel leaves the player where they were.

### The travel ticket

Minecraft 1.20.5's Transfer packet carries only host and port. **Servers reject transfers unless `accepts-transfers=true`, cookies up to 5 KiB persist across transfers but not across disconnects, and resource packs are kept** ([Minecraft Wiki 24w03a](https://minecraft.wiki/w/Java_Edition_24w03a); [Packets](https://minecraft.wiki/w/Java_Edition_protocol/Packets)). Because the client carries the cookie, Passage signs it with HMAC-SHA256, binds it to the client's address and recommends a **60-second expiry** ([Passage](https://passage.scrayos.net/advanced/cookies)). Hytale's referral carries at most 4096 bytes and logs "unauthenticated - plugins must validate!". Its docs ask for source allow-lists, a signature and replay protection ([Hytale Docs (community)](http://hytale-docs-mcp.craftserve.com:8080/protocol/server-transfer/)). Roblox teleport data can be replayed for up to 48 hours, so valuable state stays out of it ([Roblox DevForum](https://devforum.roblox.com/t/to-what-extent-can-exploiters-modify-teleportdata/2794032)).

These networks share an HMAC secret because their servers trust each other. Strangers' worlds have no shared secret, so chiacraft should use a public-key signature *(inference)*. **The origin world signs `chiacraft travel v1 / player: <login key> / from: <origin world> / to: <destination world> / link: <id> / return: <origin portal position> / issued / expires (60 s) / nonce`.** The destination accepts the ticket when six checks pass: it holds the link with both signatures and no tombstone, the origin's signature verifies against the key in that link, `to` names itself, **the player key equals the connection's remote endpoint id**, the ticket is unexpired, and the nonce is unseen. The endpoint-id check is free channel binding: iroh's handshake already proves the player holds the login key, and no intermediary can speak for them, the lesson of BungeeCord's unsigned forwarding ([PaperMC](https://docs.papermc.io/velocity/player-information-forwarding)). The ticket is *evidence of the route*, not identity. A world that is open to anyone still admits a direct join by address. The ticket is what gets the player an arrival at the linked portal, admission to "via links only" worlds, and rate limits and blocks applied per origin world. The admission reply mirrors Hytale's `setCancelled` and `referToServer`. It is either accepted, with an arrival position and a reservation timeout; refused, with a reason, or silent for a blocked sender; or redirected to spawn.

### Commit, release and the return ladder

At commit the client shows the transition, swaps `Content` (the packages are already cached), and enters play. The destination confirms "arrived". Only then does the client tell the origin to **release**. The origin saves the player standing just outside its portal. If the confirmation doesn't arrive within the timeout, the player is restored at the origin portal *(inference, after OpenSimulator's release callback)*. The player's own world keeps running in its `Scope`, so the release costs nothing locally. Inventories stay per world, as today, so nothing has to move exactly once. The plan's "carry inventories between us" proposal is a separate two-phase protocol and stays out of slices 2–5.

Returning is a ladder *(inference)*. Velocity has a `try` list and `failover-on-unexpected-server-disconnect`, and Server Redirect falls back to a configured address ([Velocity configuration](https://docs.papermc.io/velocity/configuration); [Server Redirect](https://modrinth.com/mod/YqkxTQEh)). chiacraft has no proxy, so the client carries the list itself. Walking into the destination's portal for the same link travels back with a ticket signed by the destination world, landing at the origin portal. If the destination drops, the client returns to the origin portal, which is usually the player's own running world. If that origin is someone else's world and is offline too, the client goes to the player's home world, and failing that to the title screen. Minecraft cookies die on disconnect, so **chiacraft must persist the return ticket locally**: origin key, portal position, link id and the origin's lock hash. After a crash the next start then offers "Return to X". Keep the origin's lock pinned in the package cache during the visit so the trip back needs no download. Hypergrid refuses a teleport outright when the visitor's home cannot be reached ([Hypergrid Protocol](http://opensimulator.org/wiki/Hypergrid_Protocol)). A self-contained ticket avoids that dependency.

**Arrival placement.** Place the player in front of the portal, outside its trigger volume and facing out. Search for a safe spot: not inside solid blocks, not over void or lava. Fall back to world spawn. EVE's timers suggest two protections: a short session-change lock and a 60-second post-jump cloak ([EVE forums archive](https://forums-archive.eveonline.com/topic/282359)). chiacraft should give arrivals 3–5 seconds of grace (no damage, no pushing) and a re-entry cooldown: the player must step out of the trigger and wait a few seconds. Only one travel may be in flight per player. Second Life calls corner double-crossings "generally unsatisfactory" and crossing "a rather brittle operation" ([SL Wiki](https://wiki.secondlife.com/wiki/Region_crossing)). A visitor who is already present when a link is revoked may stay until they leave, and their return route still works. That is the simplest choice and an owner-policy question.

## Open to requests, closed to auto-acceptance

Every open inbox in a decentralised network has been flooded, and the fixes that worked were closing the default, proactive filtering and shared lists. **Matrix's August 2025 invite spam carried abuse in the user IDs and room names themselves, before any acceptance** ([Frederickson](https://www.terracrypt.net/posts/matrix-spam.html)). Matrix responded with policy servers, then an invite-blocking toggle in v1.18, which it explicitly calls "a minimal first step" ([Matrix v1.18](https://matrix.org/blog/2026/03/26/matrix-v1.18-release/); [policy servers](https://matrix.org/blog/2025/04/introducing-policy-servers/)). **After the February 2024 bot wave, Mastodon made new instances not-open by default** ([TechCrunch](https://techcrunch.com/2024/02/20/spam-attack-on-twitter-x-rival-mastodon-highlights-fediverse-vulnerabilities/embed/)). Proof-of-work alone fails against botnets ([Laurie & Clayton, 2004](https://www.cl.cam.ac.uk/~rnc1/proofwork.pdf)). It works only when weighted by reputation, cheap for known senders and costly for unknown ones ([Liu & Camp, 2006](https://sites.cs.ucsb.edu/~rich/class/cs293b-cloud/papers/lui-pow.pdf)).

That evidence sits in tension with the plan's "defaults are open". The resolution: **worlds receive requests and visitors by default, unknown requests are quarantined and rate-limited, and nothing from a stranger is ever auto-accepted** *(inference)*. The inbox renders unknown requests collapsed: proposed name with fingerprint, no note until opened. Blocks are local, silent and per key or per world. Matrix lets report endpoints return the same answer whether or not the target exists ([Matrix v1.18](https://matrix.org/blog/2026/03/26/matrix-v1.18-release/)); likewise, a blocked sender learns nothing. Keys from 24 words cost nothing, so per-key bans are easy to evade. Fediverse admins answered by limiting the issuing *server* ([Ubuntu advisory](https://discourse.ubuntu.com/t/advisory-spam-invite-incident-2024-09-13/48034)). chiacraft's equivalent is **blocking an origin world, which blocks every arrival it vouches for** *(inference)*. Shared denylists should be FIRES-style signed advisories that anyone publishes and clients subscribe to ([FIRES](https://github.com/FediMod/fires)). A single list's entry should hide or quarantine rather than hard-block, because Bluesky's subscribable lists showed how a list owner can punish people "for everyone" out of revenge ([Virtual Curiosities](https://www.virtualcuriosities.com/?p=2957)). Proof-of-work belongs only on requests from unknown senders and is not needed in slice 3.

Travel threats map onto known mitigations:

| Threat | Mitigation | Basis |
|---|---|---|
| Griefers arriving through portals | destination admission per origin world and per player; an optional visitor role (no build, break or drop) | OpenSim `ForeignAgentsAllowed` + `AllowExcept` ([config](https://pastebin.com/GH3p6cU9)); VRChat trust ranks ([wiki](https://wiki.vrchat.com/wiki/Trust_Rank)) |
| Trapped or camped arrival point | client-side safe-spot check, arrival grace, and a "Back"/"Go home" the host cannot disable | SL landing points; EVE gate cloak |
| Look-alike or impersonated world | portal binds the world key; client checks the peer key before "Arrived at X"; petname and fingerprint shown | Petnames paper |
| Forced or huge downloads | the existing consent sheet with size, signer and trust, never skipped on step-through | Phase 2 slice 5 |
| Ticket replay | 60 s expiry, nonce cache, `to` binding, no valuable state in tickets | Passage; Roblox |
| Arrival floods | per-origin and per-key arrival limits, capacity cap, cheap admission before chunks load | Velocity anti-bot practice ([Sonar listing](https://www.boxtoplay.com/en/minecraft-hosting/minecraft-server/modrinth-plugins/sonar-49697)) |
| Visitor's IP exposed | relay-only connections to untrusted worlds until admitted | [iroh security & privacy](https://docs.iroh.computer/concepts/security-privacy) |

The last row needs a caveat. iroh's docs say **direct connections require exchanging IP addresses and relays still see who talks to whom**, and list relay-only mode as *upcoming* ([iroh docs](https://docs.iroh.computer/concepts/security-privacy)). Whether 1.4.1 ships it is unverified. "Always relay for worlds I haven't trusted" is the right default once it exists. The plan's rule 5 ("players are safe in any world") is satisfied by the client-side controls in the table: safe-spot check, grace, unblockable return, consent and relay mode. Those protect the *player* whatever the host does. The visitor role protects the *world* and stays the owner's choice.

## Six changes the plan should make

| Plan text today | Change | Why |
|---|---|---|
| Slice 1: "Joins go out through the hosting endpoint" | With per-world keys, joins go back to the account endpoint; the world endpoint carries the world key | Different keys no longer collide on the relay, and the guest's identity stays the login key |
| Slice 2: "a key per world" | Hardened derivation with a **random** index and a generation; account-signed world certificate and move notice until the world DID; never two live copies (dial self before hosting) | A sequential index collides across machines; rotation needs the account above the world key |
| Slice 2: discovery unspecified | n0 DNS + Mainline DHT + mDNS + saved hints, relay-only publishing, configurable origins; `chiacraft/status/1` and `chiacraft/worlds/1` | Rule 1, and liveness needs a direct ping |
| Slice 3: "inbox" | Outbox retry + the owner's game answering for all its worlds + an `inboxes` field reserved for mailboxes | Worlds are offline most of the time |
| Slice 4: "portal blocks bound to a link" | Built-in block, link id only, owner-checked binding, positions world-local | Packages differ per world; anyone can `/give` today |
| Rule 2: "defaults are open" | Open to receiving requests and visitors; never auto-accept strangers; local silent blocks and origin-world blocks on by default | Matrix and Mastodon reversed fully open defaults after abuse |

Several questions remain open. Nobody has published dns.iroh.link's record retention, so it is unknown how fast a stopped world "disappears". The cost of several `Endpoint`s per process is unmeasured. iroh's relay-only mode and `DhtAddressLookup`'s defaults were not verified. iroh-gossip for push presence was not researched. Chia DID specifics (how a DID record updates a world's current key) were out of scope. No source gave real inbox size or rate limits; the figures above are judgement calls.

## Conclusion

The research shifts the weight of Phase 3. Portals are the visible feature, but **the hard engineering is in reachability**: worlds that are offline most of the time, keys that must exist in exactly one place, and requests that have to find an owner who is not playing. The design answers all three with things chiacraft already has. The account identity key vouches for world keys exactly as it vouches for content keys. The owner's game, running on any screen, becomes the inbox. The per-world `Scope` from slice 1 makes the origin a fallback that is always there, which no centralised network gets for free.

The second takeaway is that **every signature in the design is local evidence checked by whoever controls the resource**: the link by the destination at admission, the ticket by the destination against its own link copy, the revocation by the world that issued it. Nothing needs a global registry, a chain or a shared secret, which keeps rule 3 intact: links, bans and inventories stay off the chain. It also means that when world DIDs arrive in Phase 4, they replace only the world certificate and move notice. The link, ticket and portal formats survive unchanged, provided their signatures carry key ids from the start.
