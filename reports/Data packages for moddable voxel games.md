# Pin content by BLAKE3, swap it between worlds

The tentative plan is mostly right, and the prior art backs most of its shape. TOML records plus an `assets/` folder plus `package.toml` is a sound authoring format. Pushing packages from the host over the existing iroh connection is what Luanti, Hytale and Factorio already do in spirit. Swapping a whole frozen `Content` only between worlds, with old ones leaked and interned by hash, avoids the remapping bugs Fabric and NeoForge still fight. Four decisions should change. First, **package identity should be BLAKE3 of a canonical manifest that lists per-file hashes, not SHA-256 of an archive**. That gives verified streaming, safe resume, per-file dedup and later multi-source download, and changing the hash after worlds have pinned packages would break every pin. Second, **the package list should not be a field in the hello; it needs its own configuration phase** (have / need / declined, then download, validate, compare the hash of the loaded `Content`, acknowledge), modelled on Minecraft's 1.20.2+ configuration state. Third, **the cache should be a content-addressed blob store, not extracted `<hash>/` folders**. That removes zip slip and archive bombs as a class of problem. Fourth, **manifests should be signed by a dedicated content-signing subkey** derived on its own hardened path and certified by the account (later the DID), never by the login or iroh key. Signatures should sit in a detached envelope so endorsements never change the pinned hash. Everything else in the plan stays, with additions: a format version with load-time upgraders, mandatory size declarations and decode limits, narrow default trust scopes, and an "unknown block" placeholder so a missing package never destroys save data. Because Weft's `freeze()` already takes per-mod `RawRegistrar`s, sorts ids by name and collects every error (`crates/engine/src/content.rs`), packages can compile into that same input, and the engine change stays small.

## TOML records hold up, if the id comes from the path

No format has won across the industry. Each engine picks what fits its ecosystem. Minecraft uses strict JSON in a namespaced tree where `data/<ns>/<registry>/<path>.json` becomes the id `<ns>:<path>`. Tags merge across packs unless they set `"replace": true`, the last-loaded file wins for everything else, and the ordered pack list is saved in the world ([Data pack, minecraft.wiki](https://minecraft.wiki/w/Data_pack)). Vintage Story uses JSON-like asset files. Its `variantgroups` plus `*ByType` maps expand one file into hundreds of blocks ([VS Modding:Variants](https://wiki.vintagestory.at/Modding:Variants)), and JSON-Patch files let one mod edit another's assets ([VS JSON Patching](https://wiki.vintagestory.at/Modding:JSON_Patching)). Hytale, in Early Access since January 2026, uses JSON assets with `Parent` inheritance and a `manifest.json` carrying Group, Name, Version, Dependencies, OptionalDependencies and LoadBefore ([docs.hytale.com: Asset packs](https://docs.hytale.com/creating-content/asset-packs/)). Veloren uses RON through a typed asset cache that inspired the `assets_manager` crate ([assets_manager](https://github.com/a1phyr/assets_manager)). Luanti is the outlier: its content is Lua code that calls registration functions, and only `mod.conf` and media are data ([Luanti Lua API](https://api.luanti.org/)). That keeps it from validating or patching content statically.

TOML is a defensible choice for Weft. Its known weakness is deep nesting: commenters on the spec say deeply nested tables "become unreadable" ([toml-lang/toml#781](https://github.com/toml-lang/toml/issues/781)). **TOML 1.1.0 (December 2025) allows newlines and trailing commas in inline tables** ([TOML 1.1.0 release](https://sourceforge.net/projects/toml.mirror/files/1.1.0/)), which takes away much of that pain for loot pools and similar trees. Whether the Rust `toml` crate supports 1.1 yet was not verified, so check before relying on it. TOML's advantages in Rust are real. `serde_spanned` gives per-value source spans and is "mostly only supported by the TOML serde library" ([Rust users forum](https://users.rust-lang.org/t/any-hacks-to-get-spans-with-serde/139939)). Taplo and Tombi bind a JSON Schema through a `#:schema` directive ([Tombi docs](https://tombi-toml.github.io/tombi/docs/comment-directive/schema-document-directive)). Modders therefore get editor validation, and the loader can point at the exact line of a bad value. The practical split is TOML for records (blocks, items, recipes, tags, sound indexes, simple loot, the manifest) and JSON for models. Weft already reads Blockbench's Java block-model JSON and Bedrock `geo.json` for entities (`crates/engine/src/block_model.rs`), so that half needs no decision. Accepting `.json` for every def registry through the same serde types costs nearly nothing and covers generated content and deep trees.

The structural lessons count for more than the syntax. The id should come from the file path (`defs/<registry>/<path>.toml` becomes `<pkg>:<path>`), as in Minecraft, so it is never repeated inside the file. Item and block definitions should be bags of optional typed components rather than one large struct. Minecraft moved to this in 1.20.5: an item type holds default components, a stack stores only its differences, and a `!component` entry removes a default ([Data component format](https://minecraft.wiki/w/Data_component_format)). Weft's `Content` already has a `components` table and `RawValue` lists, so packages fit the engine's own model. Templates are worth having: a `parent` with documented merge rules (tables merge, scalars and arrays replace), as Hytale's items do ([Hytale Items](https://pre-release.docs.hytale.com/assets/item/items/)), plus a small variant expander. Avoid Vintage Story's first-match-wins wildcard maps. Its wiki records patches that silently replaced arrays after updates, index paths that broke when the target file changed, and no tool to find patches that apply but do nothing ([VS JSON Patching](https://wiki.vintagestory.at/Modding:JSON_Patching)). If cross-package editing is offered, it should be semantic (override by id, merge fields, append to or remove from a tag) and should warn when a patch is a no-op.

Versioning needs two numbers from day one. Minecraft changes its pack format constantly. In 25w31a it replaced the single `pack_format` with `min_format`/`max_format` ranges and minor versions for additive changes ([Pack format](https://minecraft.wiki/w/Pack_format)), but it never migrates old packs, so every breaking bump lands on pack authors. Weft can do better: put `format = "1.0"` (content-format major.minor) in `package.toml`, and have the engine run in-code upgraders for older formats at load time. Package versions should be strict semver with cargo-style ranges, which removes Vintage Story's documented ambiguity over whether a listed version is a minimum or an exact match ([VS Modinfo](https://wiki.vintagestory.at/Modding:Modinfo)). Luanti's `depends` has no versions at all ([Luanti mods](https://api.luanti.org/mods/)). There is also a distinction the plan doesn't yet name. **`package.toml` dependencies are ranges, for authors; a world's pin list is a lockfile of exact hashes, for players.** This mirrors Cargo.toml and Cargo.lock. The world owner's tool resolves ranges once, when the world's package set changes, and joining players never resolve anything. They take the lock. Validation should follow Minecraft's transactional `/reload`, which keeps the old data when a reload fails ([Data pack](https://minecraft.wiki/w/Data_pack)). It should use `deny_unknown_fields` to catch typos, resolve every cross-reference in a link pass, and report every error in every package before refusing a world. Weft's `freeze()` already returns `Vec<String>` errors rather than stopping at the first, so the loader only has to add spans.

## Hash the manifest with BLAKE3, not the archive with SHA-256

Every system that pushes content to joining players converges on "announce hashes, fetch only what's missing". They differ in how well they verify. Minecraft names a server pack by UUID, URL and an *optional* SHA-1 of the zip, with a 250 MiB cap ([Server.properties](https://minecraft.wiki/w/Server.properties)). If the hash is missing or malformed, the client skips verification ([Java Edition protocol/Packets](https://minecraft.wiki/w/Java_Edition_protocol/Packets)). The 1.20.3 notes, seen only in search summaries, say a pack without a hash is downloaded again before every application ([minecraft.net 1.20.3-pre1](https://minecraft.net/en-us/article/minecraft-1-20-3-pre-release-1)). SHA-1 itself has been broken for collisions since SHAttered ([shattered.io](https://shattered.io)). Garry's Mod FastDL is worse: "Files aren't checked for their contents", so updated files don't reach clients, and the legacy in-game download can be spammed to lag servers ([GMod Serving Content](https://wiki.facepunch.com/gmod/Serving_Content)). Luanti is the closest prior art to the plan and the best model. The server announces a SHA-1 for every media file. The client stores files under `cache/media/<sha1-hex>`, recomputes the hash both on receipt *and* when loading from the cache, and requests only what it lacks ([Luanti clientmedia.cpp](https://github.com/luanti-org/luanti/blob/master/src/client/clientmedia.cpp)). Optional HTTP mirrors serve files named by hash, with fallback to in-band transfer ([Luanti remote media](https://docs.luanti.org/for-server-hosts/remote-media/)). Factorio provides the right *semantics*. Joining offers to download "the exact same mod versions as the server is using", startup settings sync along with the mods ([Factorio Installing Mods](https://wiki.factorio.com/Installing_Mods)), and checksums are compared with peers when joining to catch locally edited mods ([Factorio Multiplayer](https://wiki.factorio.com/Multiplayer)). Hytale states the player expectation for 2025–2026: "You should be able to join any modded Hytale server without downloading external mods or juggling client packs" ([Hytale modding strategy](https://hytale.com/news/2025/11/hytale-modding-strategy-and-status)).

The choice of hash matters more than it looks, because it is permanent once worlds pin it. A flat SHA-256 over a package is known only after the last byte arrives. A buggy or malicious host can make a player download the whole package before anything is detected. Resuming means trusting an unverified partial file. With several sources, nobody can tell which peer sent the bad bytes. iroh-blobs solves exactly this. It uses BLAKE3 verified streaming, in which **every 16 KiB chunk group is checked against the root hash as it arrives**. It supports range requests (and so resume), collections via HashSeq, a downloader that splits requests across providers, and a filesystem store with partial-content bitfields ([iroh-blobs protocol.rs](https://github.com/n0-computer/iroh-blobs/blob/main/src/protocol.rs); [downloader.rs](https://github.com/n0-computer/iroh-blobs/blob/main/src/api/downloader.rs)). In bao the length is part of the tree, so a size the host declares in the hello is bound to the hash, and a host that lies about it is caught within about one chunk group. The catch is maturity. The README says "not yet considered production quality" ([iroh-blobs README](https://github.com/n0-computer/iroh-blobs)). Releases break roughly monthly: 0.104.0 shipped on 2026-10-28, and most 0.97–0.103 `.0` releases are yanked ([crates.io iroh-blobs](https://crates.io/crates/iroh-blobs)). Its default ALPN `/iroh-bytes/4` implies a second QUIC connection, although `provider::handle_stream` can serve requests on streams of the game's own connection ([provider.rs](https://github.com/n0-computer/iroh-blobs/blob/main/src/provider.rs)). The lower layer, `bao-tree`, is wire-compatible with bao and adds multi-range queries ([bao-tree](https://github.com/n0-computer/bao-tree)). It is a much smaller dependency.

| Property | SHA-256 + custom stream (plan) | BLAKE3 + bao-tree on own streams | BLAKE3 + iroh-blobs |
|---|---|---|---|
| Detects bad data | Only at the end | Per 16 KiB group | Per 16 KiB group |
| Safe resume | Custom, unverified partial | Range requests, verified prefix | Built in (bitfields) |
| Multi-source with blame | No | Possible, own code | Built in (`SplitStrategy::Split`) |
| Per-file dedup across versions | Only if per-file hashed | Yes (manifest of blobs) | Yes (HashSeq) |
| Dependency risk | None | Small, stable layer | Pre-production, monthly breaks |
| Fits "one iroh connection" | Yes | Yes | Via `handle_stream` wrapper |

**Recommendation: BLAKE3 now, `bao-tree` over the planned extra streams first, iroh-blobs later.** The identity hash fixes the long-term direction. Picking BLAKE3 means a later move to iroh-blobs, to other players as sources, or to anyone's mirror serving files by hash needs no change to any world pin. One caveat: before wrapping iroh-blobs' `handle_stream` on the shared game connection, check in its source whether a blob error closes only the stream or the whole connection. Its protocol docs say the provider closes the connection on missing or invalid data.

What gets hashed matters as much as which hash. Hashing zip bytes is fragile, because timestamps, compression level and entry order change the bytes without changing the content. Go's `h1:` module hash hashes a sorted list of per-file SHA-256s and names, and explicitly ignores "compression method, per-file modification times, and other metadata" ([pkg.go.dev dirhash](https://pkg.go.dev/golang.org/x/mod/sumdb/dirhash)). BitTorrent v2 builds a merkle root per file so that "identical files always result in the same root hash" ([BEP 52](https://www.bittorrent.org/beps/bep_0052.html)). IPFS shows the opposite trap: chunking parameters mean "two identical files can produce different CIDs" ([IPFS docs](https://docs.ipfs.tech/concepts/content-addressing/)). The package identity should therefore be **BLAKE3 of a canonical manifest**: a deterministic encoding of format, package id, version, creator key, dependencies by hash, and the sorted `[(path, size, blake3)]` file list. That maps directly onto a HashSeq. A 1.1 release that changes one texture costs a one-file download. Factorio's checksums could differ between identical mod versions because of conditional `require()` ([Factorio forums](https://forums.factorio.com/viewtopic.php?p=270761)). The lesson is that identity must depend only on bytes, never on settings or load order. Per-world settings belong in the world's own manifest, which gets its own hash.

The plan's "package list in the connection hello" should become a phase rather than a field. Since 1.20.2 Minecraft has had a configuration state between login and play. In it the server sends registries, tags and resource packs, the client validates everything when it receives Finish Configuration and acknowledges, and play can send the client back into configuration ([Packets](https://minecraft.wiki/w/Java_Edition_protocol/Packets)). Its "known packs" negotiation lets the client say what it already has, but it keys packs by `namespace:id:version` *strings*. Vanilla in practice recognises only `minecraft:core` and sends all custom data in full ([Registry data](https://minecraft.wiki/w/User:LassiPulkkinen/sandbox/Java_Edition_protocol/Registry_data)). Content hashes make the same negotiation exact. The proposed flow: the hello carries the world-lock hash. The host sends `[(root_hash, total_size, display_name)]`, and the client replies have / need / declined. Downloads run with per-package status reported back to the host, copying Minecraft's result enum (accepted, downloaded, loaded, declined, failed download, failed reload, discarded) so the host can see failures that Minecraft logs only on the client. The client builds and validates the full set, sends the hash of the `Content` it actually froze, and the host admits it to play. Cap the number of announced packages (Minecraft caps known packs at 64 entries) and the size of every message.

The cache plan needs the same correction. Extracting into `run/cache/packages/<hash>/` reintroduces filesystem paths chosen by package authors. Zip Slip showed how entries named `../../evil.sh` led to file overwrite and often RCE across thousands of projects ([Snyk Zip Slip](https://security.snyk.io/research/zip-slip-vulnerability)). A blob store at `run/cache/blobs/<blake3>` instead, with manifests resolving logical asset names through an in-memory map, never joins an author's string onto a path. Prior art on eviction is weak. Minecraft's 1.20.3 notes, again via search summaries, say downloaded packs "are no longer automatically cleaned" ([minecraft.net 1.20.3-pre1](https://minecraft.net/en-us/article/minecraft-1-20-3-pre-release-1)), and Luanti seems never to evict. Weft should keep a pins index (packages referenced by worlds on disk and by recently joined worlds) and run LRU eviction under a budget that never evicts a pinned hash. iroh-blobs' GC with a protect callback is the same pattern ([iroh-blobs gc.rs](https://github.com/n0-computer/iroh-blobs/blob/main/src/store/gc.rs)). Factorio's portal keeps deprecated mods downloadable so that "sync mods with save" keeps working ([factorio.com blog](https://factorio.com/blog/21)). The equivalent rule here: a host must keep serving every hash its world pins, and should serve *only* those hashes, to authenticated session peers, with per-peer stream and bandwidth limits.

## Build a new Content, never remap the old one

Every mature system stores names on disk, uses numeric ids only in memory and on the wire, and has the client adopt the server's id assignment. In Minecraft's synced data registries, "the ordering of the entries ... defines the numeric IDs", and an entry the server doesn't send "will not exist in the game session" ([Registry data](https://minecraft.wiki/w/Java_Edition_protocol/Registry_data)). NeoForge documents synced integer ids as something that "should only be used in networking contexts" ([NeoForge docs](https://docs.neoforged.net/docs/concepts/registries/)). Luanti stores a name-to-id map inside every MapBlock and turns unknown names into a special "unknown" node instead of failing ([Luanti basic data structures](https://docs.luanti.org/for-engine-devs/basic-data-structures/)). Weft already follows this rule. `ids.txt` maps stored world ids to names "so adding or removing mods never shifts what is stored on disk" (`crates/engine/src/saves.rs`), and `freeze()` assigns ids "in name order, so they do not depend on which mod finished registering first".

How the loaders swap is the instructive part. Fabric remaps a live registry in place. Its tables are cleared before reinsertion, so an exception mid-loop leaves a partial registry. It treats holes and unknown remote ids as fatal, and it fires `RegistryIdRemapCallback` so caches holding raw ids can rebuild ([Fabric SimpleRegistryMixin](https://raw.githubusercontent.com/FabricMC/fabric/1.21.4/fabric-registry-sync-v0/src/main/java/net/fabricmc/fabric/mixin/registry/sync/SimpleRegistryMixin.java)). NeoForge unfreezes, clears, re-registers and refreezes each registry, then reverts to a frozen snapshot on leave ([NeoForge RegistryManager](https://raw.githubusercontent.com/neoforged/NeoForge/1.21.x/src/main/java/net/neoforged/neoforge/registries/RegistryManager.java)). Factorio rebuilds all prototypes in a fresh Lua state. Since 1.1.61 it syncs mods and settings in one pass to cut the number of restarts ([Factorio 1.1.61](https://forums.factorio.com/viewtopic.php?p=570127)). Building a new immutable `Content` and switching to it removes the whole partial-remap class of bugs. **The plan's "swap only when no world is loaded, leak and intern each frozen `Content` by hash" is the right call.** `ArcSwap` would free old generations ([arc-swap](https://docs.rs/arc-swap/latest/arc_swap/)), but any guard held across a swap silently pins stale content, and native mods want `&'static`. Memory grows only with the number of distinct content sets a process visits, which is usually a handful. The engine change can be tiny: `CONTENT` is a `OnceLock<Content>` behind `content() -> &'static Content` (`crates/engine/src/content.rs`). Replacing it with an atomic pointer to leaked, hash-interned boxes keeps every caller's signature unchanged.

The failures the others hit tell us what the swap must also do. Minecraft reconfiguration kicked players when a play-state `system_chat` packet arrived after Start Configuration ([MC-270378](https://bugs-legacy.mojang.com/browse/MC-270378)), and re-entry cleared chat ([MC-265250](https://bugs.mojang.com/browse/MC-265250)). Factorio once compared the *enabled* mod list instead of the *loaded* one, and clients desynced instantly ([Factorio forums 20026](https://forums.factorio.com/20026)). A Weft swap therefore unloads the world and drops every chunk, mesh, entity and `ItemStack` that refers to old ids. It joins or cancels meshing and worldgen workers, which are the most likely Weft-specific source of stale ids. It switches the connection into a configuring state that refuses gameplay packets, freezes or interns the new `Content`, rebuilds atlases, and only then accepts the world. The admission check compares a hash of the *loaded* `Content`, not the package list. A `content_epoch` stored next to any cached id lets debug builds assert that the id still belongs to the current generation, the way Fabric's debug flags catch ids that don't round-trip. The client's home `Content` stays interned, so leaving a world returns to it at no cost, like Fabric's `unmap` and NeoForge's `revertToFrozen`. Unknown names in `ids.txt` should map to a placeholder block that keeps the original name. NeoForge warns that missing entries "will be deleted from the save file on next save", and Weft should not lose data that way.

The "native first, then packages" ordering gains strength from a decision already in `notes/PLAN.md`. Each native mod set is its own universe, entered with a restart. Inside one process the native set never changes, so **native-first ordering means native ids never move for the life of the process**. Only package ids shift between worlds, and native mods need to re-resolve by name only the package content they reference. That is a small, well-scoped callback rather than Fabric's everything-listens-to-remap. Weft today sorts all blocks globally by name (`blocks.par_sort_by(... name ...)` in `freeze()`), so the change is one sort key, `(is_package, name)`. Sorting should be byte-wise on the id string, never locale-aware. One more design choice follows. Two processes with the same game version, the same native set and the same package hashes produce identical ids deterministically, so the host doesn't need to send an id table. The `Content` hash comparison proves agreement and gives a clean "versions differ" refusal when they don't match. Reserve a message type for a server-sent table in case a future feature, such as client-only entries, breaks determinism. Minecraft's dynamic registries still need a world restart even with `/reload` ([Data pack](https://minecraft.wiki/w/Data_pack)). Weft's swap at world boundaries during portal travel is already more ambitious than vanilla. Hot-adding packages mid-world (play back into configuration) can wait.

## Signatures answer who; hashes answer what

A pinned content hash already guarantees integrity, so signatures only have to answer "who made this, and who vouches for it". That separation drives the signing design. The 2025–2026 registry trend is centralised workload identity. crates.io Trusted Publishing issues short-lived OIDC publish tokens ([Rust blog 2025-07-11](https://blog.rust-lang.org/2025/07/11/crates-io-development-update-2025-07)). PyPI's PEP 740 attestations are Sigstore-based ([PyPI blog](https://blog.pypi.org/posts/2024-11-14-pypi-now-supports-digital-attestations/)). Sigstore keyless signing binds an ephemeral key to an OIDC identity through Fulcio and logs it in Rekor ([Sigstore overview](https://docs.sigstore.dev/about/overview/)). Rekor v2 reached GA in October 2025 ([Sigstore blog](https://blog.sigstore.dev/)). All of this depends on central identity providers and hosted logs, which conflicts with "no central service" and with LAN play. Players already hold what keyless signing exists to replace: a long-lived key derived from their words. The better template is minisign. It produces detached Ed25519 signatures over a BLAKE2b prehash, carries a key id, and has a "trusted comment" covered by a global signature, so the metadata can't be altered ([minisign docs](https://jedisct1.github.io/minisign/)). OpenBSD's signify signs a checksum list rather than each file ([signify paper](https://www.openbsd.org/papers/bsdcan-signify.html)), which is exactly a manifest. TUF supplies the ideas Weft needs later: signed lengths that stop "endless data" downloads, monotonic versions and expiry against rollback and freeze, N-of-M thresholds, and root rotation signed by both the old and the new keys ([TUF spec](https://theupdateframework.github.io/specification/latest/)). Its snapshot and timestamp roles exist to prove a central repository is fresh, and Weft has no central repository.

The plan to sign "with the creator's account identity key" should change in one respect. Ed25519 has no built-in context, so applications must prefix their own domain tag ([RFC 8032](https://www.rfc-editor.org/rfc/rfc8032#section-5.1)). SSH signatures make a namespace mandatory for exactly this reason ([PROTOCOL.sshsig](https://github.com/openssh/openssh-portable/blob/master/PROTOCOL.sshsig)). The account key will also prove joins and, later, control a DID, so a package signature must never be replayable as anything else. The login key is already derived on its own hardened path and becomes the iroh key (`notes/PLAN.md`). The consistent move is a **third derived key used only for content signing, certified once by the account key and later listed by the DID**. A leaked content key then doesn't compromise the account, and the DID can rotate it on chain. That is the "chain only where it adds trust" rule at work. The signed preimage should be `"weft:v1:pkg-manifest\0" || manifest_hash`, with sibling purposes for `reviewer-list`, `key-rotation` and `revocation`. The signature lives in a detached envelope `{manifest_hash, key_id, sig}`. Co-signers and reviewer endorsements can then be added without changing the hash a world pins. The canonical manifest must use an encoding with no re-serialisation ambiguity, such as deterministic CBOR or a fixed binary layout. That means `package.toml` is the author-facing source, and `weft package build` produces the hashed and signed artifact, the same relationship Cargo.toml has to a published crate. Every player has a key, so signing costs nothing. The only unsigned path needed is local development.

Consent must be rare and specific, or it means nothing. Felt et al. found that only 17% of participants paid attention to Android install-time permissions ([SOUPS 2012](https://www.cs.berkeley.edu/~afelt/permissions-soups2012.pdf)). SSL-warning click-through ran about 70% in Chrome against about 33% in Firefox, purely from design differences ([Akhawe & Felt](https://www.usenix.org/conference/usenixsecurity13/technical-sessions/presentation/akhawe)). Minecraft's prompt shows no size or author, and `require-resource-pack` disconnects anyone who declines ([Server.properties](https://minecraft.wiki/w/Server.properties)). The choice is coerced, so players learn to click Accept. Chrome's model is better: an update that adds permissions disables the extension until the user approves it, and ordinary updates don't ask ([Chrome permission warnings](https://developer.chrome.com/docs/extensions/develop/concepts/permission-warnings)). For Weft, the join sheet should show the host, the exact download size from the manifests, each package's creator as a petname plus a key-fingerprint glyph, and a "new to you / trusted / endorsed" status. **Trust "per creator and per package" stays, but the default scope should be narrow**: this package hash, or everything this world pins. "Always allow content from this creator" is a deliberate second action. Re-prompt only on meaningful change: a new creator key, a large jump in size, a new content-rating tag, a key rotation or revocation notice, or a withdrawn endorsement. A routine version bump earns a toast. Display names are spoofable and a key is not an identity. Scuttlebutt's local petnames ([SSB protocol guide](https://ssbc.github.io/scuttlebutt-protocol-guide/)) and Zooko's-triangle reasoning ([Petname systems](http://www.skyhunter.com/marcs/petnames/IntroPetNames.html)) argue for a petname on first trust and an explicit "not the Ava you trust" warning when a new key arrives with a confusable name. Revocation should trigger a re-prompt, never deletion, because a thief can issue one too. Fractureiser, the 2023 incident in which compromised CurseForge accounts uploaded trojaned versions of legitimate mods ([fractureiser README](https://github.com/fractureiser-investigation/fractureiser/blob/main/README.md)), is the case for reviewer lists. These should be signed, versioned, expiring and opt-in, in the shape of Nostr's NIP-51 replaceable lists ([NIP-51](https://github.com/nostr-protocol/nips/blob/master/51.md)) with TUF thresholds. They are a later slice, but the envelope should allow for them now.

"Data only" doesn't mean safe, which is why the limits belong in the first networking slice. David Fifield's overlapping-entry zip bomb turns 42 kB into 5.5 GB ([A better zip bomb](https://www.bamsoftware.com/hacks/zipbomb/)). libwebp's CVE-2023-4863 was a heap overflow in image decoding, exploited in the wild ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2023-4863)). The defences are structural. No archives in the cache. Sizes are declared in the hashed manifest and enforced while streaming. Formats come from a short allow-list decoded by pure-Rust crates: PNG, Weft's existing WAV plus Ogg, and JSON models with depth limits. Luanti restricts sounds to Ogg Vorbis for the same reason ([client_lua_api.md](https://github.com/luanti-org/luanti/blob/master/doc/client_lua_api.md)). The Rust `image` crate's `Limits` leaves width and height unlimited by default and sets `max_alloc` to 512 MiB ([image limits.rs](https://docs.rs/crate/image/latest/source/src/io/limits.rs)), so set all three explicitly. Reasonable starting caps, which are engineering judgement and not published norms: 256 MiB per package, matching Minecraft's 250 MiB per pack; 4,096 files; 16 MiB per file; 4096×4096 textures; 1 MiB per JSON file with nesting depth 64. Decode on a worker thread under `catch_unwind` with a time budget. Offensive content can't be solved technically. Self-declared rating tags, reviewer lists the player subscribes to, and a per-player block on a creator key or package hash that shows a placeholder are the decentralised tools available.

## Conclusion

The research shifts where the risk sits. Neither the file format nor the swap is the hard part: Weft's name-ordered `freeze()` and `ids.txt` palette already solve most of what Fabric and NeoForge struggle with, and the universe rule for native mods quietly removes the worst remapping case. The decisions that are hard to undo are the ones that get written into every world: the identity hash, what that hash covers, and which key signs. Get those three right in slices 2 and 5, with BLAKE3 over a canonical manifest and a dedicated signing subkey behind a detached envelope, and every later improvement is additive. Mirrors, peer swarms, reviewer lists and DID-anchored keys all slot in without touching a pin.

Two uncertainties should be settled before committing code. The first is iroh-blobs' trajectory toward a stable release, and how its stream handler behaves on a shared connection. That decides whether slice 7 adopts it or keeps bao-tree. The second is whether the Rust `toml` crate supports TOML 1.1 inline tables, which decides how comfortable deeply nested definitions are. Neither changes a decision in the table. A missing feature in either only moves work between slices.
