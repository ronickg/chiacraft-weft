# Server-pushed content delivery and content-addressed transfer (for a Rust/iroh voxel game)

Context: our tentative plan is SHA-256 package identity, package list in the connection hello, downloads over extra QUIC streams on the same iroh connection, cache at `cache/packages/<hash>/`, verify then use. The project already depends on `iroh = "1"` (workspace Cargo.toml). Research date: 2026-10-31.

## 1. Minecraft Java server resource packs (server.properties, multi-pack since 1.20.3, verification, caching, consent)

### Takeaway
Minecraft identifies a server pack by (UUID, URL, SHA-1 of the zip). The hash is optional and the URL points at any external HTTP host. That gives the familiar failure modes: a missing hash means the pack is downloaded again on every join, stale caches after a mismatch (a bug that was fixed), and a weak hash. The parts worth copying are the per-pack UUID with add/remove, the force/prompt consent model, and the detailed client status enum.

### Cited Findings
- `resource-pack` is the download URL. The pack "may not be larger than 250 MiB". The limit was 50 MiB, rose to 100 MiB in 1.15-pre5, then to 250 MiB in 1.18-rc1. The client logs download success or failure, the server does not. — [minecraft.wiki Server.properties](https://minecraft.wiki/w/Server.properties)
- `resource-pack-sha1` is an optional lowercase-hex SHA-1, "recommended". If it is malformed, the server prints "Invalid sha1 for resource-pack-sha1" at startup. — [minecraft.wiki Server.properties](https://minecraft.wiki/w/Server.properties)
- `resource-pack-id` (a UUID) was added in 1.20.3-pre1. `require-resource-pack` (20w45a / 1.17) kicks players who decline. `resource-pack-prompt` (21w15a / 1.17) holds custom prompt text as a chat component. `initial-enabled-packs` / `initial-disabled-packs` (22w42a / 1.19.3) choose data packs at world creation. — [minecraft.wiki Server.properties](https://minecraft.wiki/w/Server.properties)
- The Add Resource Pack packet (`resource_pack_push`, exists in both configuration and play) has these fields: UUID, URL (String 32767), Hash (String(40), "40 character hexadecimal, case-insensitive SHA-1 hash of the resource pack file"), Forced (Boolean), and Prompt Message (optional text component). If the hash is not a valid 40-hex string, the client skips hash verification, which probably wastes bandwidth. Remove Resource Pack (`resource_pack_pop`) takes an optional UUID; with no UUID, it removes every server pack. — [minecraft.wiki Java Edition protocol/Packets](https://minecraft.wiki/w/Java_Edition_protocol/Packets)
- The serverbound Resource Pack Response has (UUID, Result). The Result values are 0 Successfully loaded, 1 Declined, 2 Failed to download, 3 Accepted, 4 Downloaded, 5 Invalid URL, 6 Failed to reload, 7 Discarded. — [minecraft.wiki Java Edition protocol/Packets](https://minecraft.wiki/w/Java_Edition_protocol/Packets)
- Since 1.20.3 a server can send several packs that stack and can be removed one at a time. Each pack is identified by a UUID, a URI and the SHA-1 of the zip. — [PaperMC Adventure docs: Resource packs](https://docs.papermc.io/adventure/resource-pack/)
- The 1.20.3-pre1 notes cover these points. Downloaded packs go to a new downloads directory with a different layout from the old `server-resource-packs` folder. Files there "are no longer automatically cleaned (previously only up 10 packs were kept)". "If hash of a pack is not set, this pack will be redownloaded before every application". If the pack ID is missing, it is generated from the URL. The UI moved from a download screen to a toast, and pack application starts in parallel with chunk loading. A later pre-release fixed MC-251126, "Server resource pack is not redownloaded when a hash mismatch is detected with the previously downloaded version". — [minecraft.net 1.20.3 Pre-Release 1 (via search summary)](https://minecraft.net/en-us/article/minecraft-1-20-3-pre-release-1); [minecraft.wiki Resource pack](https://minecraft.wiki/w/Resource_pack). I could not open the article directly (timeout); the quotes come from search snippets.
- Server-recommended packs date back to 1.7.2 (13w36a). Players can accept or decline when they join, and `require-resource-pack=true` disconnects anyone who declines. Bedrock uses `texturepack-required` / "Shared packs" to force world packs. — [minecraft.wiki Resource pack](https://minecraft.wiki/w/Resource_pack)
- SHA-1 has been practically broken for collision resistance since the 2017 SHAttered attack. — [shattered.io](https://shattered.io)

### Inferences
- Copy the **status enum**, not the transport. A per-package state machine (Accepted, Downloaded, Verified/Loaded, Declined, FailedDownload, FailedVerify, Discarded) reported back to the host gives good host-side logs and UX. Minecraft only logs download failures on the client, which makes them hard to debug from the server.
- Make the hash **mandatory**. Minecraft's optional hash causes re-downloads on every join and lets a cache go stale. With content addressing the hash is the identity, so this problem disappears.
- Minecraft's per-pack UUID exists only because packs are named by URL. In our design the content hash already serves as the ID. We may still want a human-readable `name@version` next to the hash for UI and logs. It should be display data, never identity.
- Bound the cache. Minecraft removed the 10-pack limit and leaves cleanup to the user, which is how disks fill up. See §7.
- Consent: Minecraft's model is a prompt plus forced/optional per pack. That maps onto "this world requires N packages (X MB) from host Y: Download / Leave". Optional cosmetic packages could be declined without being kicked.

### Gaps
- I could not confirm the exact on-disk layout of the 1.20.3+ `downloads` directory, e.g. whether files are named by SHA-1 or by UUID. Both the article fetch and the wiki pages lacked it.
- I found no official statement on a client-side cache limit after 1.20.3 beyond "no longer automatically cleaned".

## 2. Minecraft configuration phase (1.20.2+) and "known packs" (1.20.5+)

### Takeaway
Since 1.20.2 there is a dedicated configuration state between login and play. In it the server sends feature flags, registry data, tags and resource packs, and the client must acknowledge before play starts. The server can send the client back into configuration from play. Since 1.20.5, "known packs" lets the client report which data packs (namespace:id plus a version string) it already has. The server can then omit the NBT bodies of registry entries from those packs, but it still lists every entry. In practice vanilla only knows `minecraft:core`, and the string versions are fragile.

### Cited Findings
- Login Acknowledged "switches the connection state to configuration". Configuration packets include, clientbound: Cookie Request, Plugin Message, Disconnect, Finish Configuration, Keep Alive, Ping, Reset Chat, Registry Data, Remove/Add Resource Pack, Feature Flags, Known Packs (`select_known_packs`), and Code of Conduct (new in recent versions). Serverbound: Client Information, Acknowledge Finish Configuration, Resource Pack Response, Known Packs, Accept Code of Conduct. Play has a clientbound Start Configuration (`start_configuration`) that sends the client back to configuration. — [minecraft.wiki Java Edition protocol/Packets](https://minecraft.wiki/w/Java_Edition_protocol/Packets)
- Clientbound Known Packs is an array of (Namespace, ID, Version) strings, for example `minecraft` / `core` / version. The client "replies with the subset of packs it also knows", in the server's order. The vanilla server waits for that reply before continuing. The protocol notes warn that the vanilla data pack can change without a protocol bump, so a vanilla server and client on different protocol-compatible patch versions may fall back to sending all registry data. — [minecraft.wiki Java Edition protocol/Packets](https://minecraft.wiki/w/Java_Edition_protocol/Packets)
- Serverbound Known Packs is a prefixed array with a limit of 64 entries. If the client lists a pack, the server "may omit that pack's NBT data from Registry Data, but not its entry listings". — [minecraft.wiki Java Edition protocol/Packets](https://minecraft.wiki/w/Java_Edition_protocol/Packets)
- Registry Data carries one registry per packet: Registry ID plus an array of (Entry ID, optional NBT). If the NBT is omitted, the data comes from the selected known packs. Entry order assigns numeric IDs starting at 0. The client accumulates the packets and validates everything when Finish Configuration arrives, then replies with Acknowledge Finish Configuration, which switches to play. A reference to a missing entry causes a disconnect. — [minecraft.wiki Java Edition protocol/Packets](https://minecraft.wiki/w/Java_Edition_protocol/Packets)
- "If an entry is not mentioned in a Registry Data packet, it will not exist in the game session, even if it exists in one of the known packs." As of 1.21.8, vanilla recognizes only `minecraft:core`, so custom data-pack data is "always sent over the network". — [minecraft.wiki Registry data (sandbox page)](https://minecraft.wiki/w/User:LassiPulkkinen/sandbox/Java_Edition_protocol/Registry_data)
- A 26.1.2 protocol reference says the same: a client that reports `minecraft:core` gets NBT only for non-vanilla entries, and a client that reports no packs gets everything in full. — [VoidMC protocol reference (registries)](https://voidminecraft.github.io/VoidMC/reference/protocol-specs/v26.1.2/registries.html)
- Feature Flags is an array of identifiers. `minecraft:vanilla` enables vanilla features, and other flags enable experiments. — [minecraft.wiki Java Edition protocol/Packets](https://minecraft.wiki/w/Java_Edition_protocol/Packets)
- Start Configuration (play → config): the server switches its outbound state immediately on sending it, and the client acknowledges. The class name is `ClientboundStartConfigurationPacket`. — [VoidMC connection lifecycle](https://voidminecraft.github.io/VoidMC/reference/protocol-specs/v26.1.2/connection-lifecycle.html); [mappings.dev history](https://mappings.dev/history/e405e76356.html)
- Mojira MC-267103 says the network-synced registries (at the time: trim material, trim pattern, biome, chat type, damage type, dimension type) are sent in configuration. Inconsistent or omitted registries used to crash the client. Since 1.20.5-pre2 they cause a clean disconnect instead. — [Mojira MC-267103](https://bugs.mojang.com/browse/MC-267103)

### Inferences
- **Direct lesson for us:** a joining client should state what it already has, and the host should send only what is missing. Minecraft keys known packs by namespace:id:version *strings*, which is why it falls back to "send everything" on patch-version drift. Keying by content hash makes the negotiation exact: matching hashes mean identical bytes. Our hello should carry `[(hash, size, display_name)]`. The client answers with a "have / need / declined" set, a direct analogue of Serverbound Known Packs.
- **Separate content from selection.** In Minecraft a known pack only supplies *bodies*. The server's Registry Data still decides which entries exist and which numeric IDs they get. For us, the world's manifest (ordered list of package hashes plus per-world config) is authoritative and is sent in full. Packages are inert content blobs. Numeric block and item IDs for the session should come from the host's assignment, not from the client's local package order.
- **Have an explicit "configuration" phase.** Model the connection as hello → configuration (package negotiation, downloads, verification, registry/ID-map sync, ack) → play. Allow play → configuration again so packages can be hot-added or swapped without reconnecting (Minecraft's Start Configuration). The client validates the whole set atomically at the "finish" step and only then acks. Partial content is never live.
- Put a limit on the count of announced packages, as Minecraft caps the client's known-pack array at 64, and on the size of every message.

### Gaps
- I did not pin the exact snapshot that introduced Known Packs. It is generally attributed to the 1.20.5 cycle, and the Mojira fix references 1.20.5-pre2, but I found no changelog line.

## 3. Luanti (Minetest) media transfer

### Takeaway
Luanti is the closest prior art to our plan. The server announces every media file's name and SHA-1. The client keeps a content-addressed cache under `cache/media/<sha1-hex>`, re-verifies cached files against the hash before loading them, and fetches only misses. Misses can come from optional HTTP mirrors (`remote_media`, which serves files named by hash) with fallback to in-band transfer. Each media file is capped at about 16.7 MB because of the UDP protocol.

### Cited Findings
- `TOCLIENT_ANNOUNCE_MEDIA` (0x3c) carries a zstd-compressed name array, a 20-byte `sha1_digest` per file, and a remote media server URL. `TOSERVER_REQUEST_MEDIA` (0x40) lists file names. `TOCLIENT_MEDIA` (0x38) sends the files in zstd-compressed "bunches" (total bunches, bunch index, file count). Dynamic media uses `TOCLIENT_MEDIA_PUSH` (0x2C: raw_hash, filename, callback_token, `should_be_cached`) and `TOSERVER_HAVE_MEDIA` (0x41: callback tokens acknowledging receipt). — [Luanti networkprotocol.h](https://github.com/luanti-org/luanti/blob/master/src/network/networkprotocol.h)
- `#define MEDIAFILE_MAX_SIZE (16700000U)`, with the comment "Due to our network protocol the maximum window size determines the maximum media size we can safely allow". The server refuses to register larger files. — [networkprotocol.h](https://github.com/luanti-org/luanti/blob/master/src/network/networkprotocol.h); [server.cpp](https://github.com/luanti-org/luanti/blob/master/src/server.cpp)
- The client cache directory is `path_cache/media`. Files are stored by `hex_encode(raw_sha1)` and written only if not already present. A SHA-1 that is not exactly 20 bytes is ignored ("ignoring illegal SHA1 sent by server"). `tryLoadFromCache` loads by hash and then calls `checkAndLoad`, which recomputes SHA-1 and compares it with the announced hash, both for cached and for received data. — [Luanti clientmedia.cpp](https://github.com/luanti-org/luanti/blob/master/src/client/clientmedia.cpp)
- If every file is cached, the client tells the server immediately. Otherwise it first fetches each remote server's hash set (`index.mth`), then fetches the missing files by hash. — [clientmedia.cpp](https://github.com/luanti-org/luanti/blob/master/src/client/clientmedia.cpp)
- Remote media: the HTTP server holds media files named by SHA-1, plus `index.mth`, which is the header `MTHS\x00\x01` followed by raw 20-byte SHA-1 digests. Files missing on the mirror, or an unreachable mirror, fall back to normal transfer. Up to 5.11 the client POSTed for `index.mth`. Since 5.12.0 it uses GET so that plain static hosting works. HTTP/2 is preferred, but official Android/Windows builds lack nghttp2. Clients need cURL and `enable_remote_media_server`. — [Luanti docs: Remote media](https://docs.luanti.org/for-server-hosts/remote-media/)
- One caveat: the archived `mtmediasrv` project notes that after the GET change the client "no longer does any negotiating", so a shared cache server needs a complete index. — (search summary of [mtmediasrv](https://gh.r-mj.com/MultiCraft/mtmediasrv); archived project, low weight)
- CSM (client-side mods) are limited by the server bitfield `csm_restriction_flags`, e.g. 0x01 blocks loading client mods, 0x02 blocks sending chat, 0x04 blocks reading item definitions; the list is incomplete. The SSCSM mod (server-sent CSM) warns "do not trust the client". — [DeepWiki: Luanti client-side scripting](https://deepwiki.com/luanti-org/luanti/6.4-client-side-scripting); [SSCSM on ContentDB](https://content.luanti.org/packages/luk3yx/sscsm/)

### Inferences
- Luanti confirms the shape of our plan: hash-named cache directory, verify on receive *and* on load from cache, request only misses, optional mirrors that are just "files named by hash". Two things to fix: use SHA-256 or BLAKE3 instead of SHA-1, and use per-package rather than per-file granularity (Luanti announces every texture, which works but makes the announce message large).
- Luanti's "dynamic media push with should_be_cached and ack tokens" is the model for adding content mid-session (cf. Minecraft play → configuration).
- Content addressing makes mirrors free and trustless. Any source (host, another player, CDN, LAN peer) can serve a hash, because the client verifies. That argues for a transport that can fetch from several providers (§5).
- Luanti's 16.7 MB cap is a transport artifact. With QUIC streams we don't need one, but we should set a *policy* cap (§7).

### Gaps
- I did not verify how Luanti handles cache eviction. It appears to have none, but I didn't confirm that in source.

## 4. Other games: Garry's Mod, Roblox, Factorio, Hytale, Valheim/Thunderstore

### Takeaway
There are three families. (a) The server pushes files itself, or points at a mirror, with weak or no verification: GMod FastDL/ServerDL. (b) The server names items in a trusted central catalog and the client downloads from that catalog: GMod Workshop, Factorio mod portal, Roblox CDN. (c) No delivery at all; users match mods by hand: Valheim/Thunderstore profile codes. Hytale (per its November 2025 modding post) commits to "server-side first": players join modded servers without installing anything, and the server supplies assets. Our P2P host-pushed model is (a) done right: content-addressed and verified, with an optional catalog later.

### Cited Findings
- **GMod `resource.AddWorkshop`**: "Adds a workshop addon for the client to download before entering the server." "Having the raw files from a workshop item does not count as having already downloaded it", so FastDL users must download again. Lua files "are not considered content" and are handled separately. There is "a 8192 downloadable file limit", shared among all `resource.Add*`. — [GMod wiki resource.AddWorkshop](https://wiki.facepunch.com/gmod/resource.AddWorkshop)
- **GMod delivery modes**: WorkshopDL, up to about 2 GB (gma) at once. FastDL needs a web server plus `sv_downloadurl`; clients try a `.bz2` first; files download one by one, which is slow for many small files; and "Files aren't checked for their contents so updating files on the server wont make the client redownload updated files". ServerDL (`sv_allowdownload 1`) is capped at 64 kB/s, is obsolete, and "Players with modified clients can spam request files to severely lag your server". Clients can choose in settings which types of files they download. — [GMod wiki Serving Content](https://wiki.facepunch.com/gmod/Serving_Content)
- **Roblox**: "Roblox servers stream all assets to the client at runtime". Meshes, textures, decals and sounds stream in as needed. `ContentProvider:PreloadAsync` prioritizes assets (e.g. for loading screens). Developers are told not to build progress bars from `RequestQueueSize`. — [Roblox ContentProvider docs](https://create.roblox.com/docs/reference/engine/classes/ContentProvider); forum view that PreloadAsync only prioritizes the CDN queue: [DevForum](https://devforum.roblox.com/t/preloadasync-is-not-actually-preloading-images/1392585)
- **Factorio**: "When trying to join a multiplayer game that uses mods, the game will offer to synchronize the mods with the server. Confirming the mod sync will automatically download and enable all mods used by the server"; it gets "the exact same mod versions as the server is using"; "mod startup settings can be synced as well". Syncing with a save uses the latest versions by default; Ctrl-click matches the exact versions. — [Factorio wiki Installing Mods](https://wiki.factorio.com/Installing_Mods)
- Factorio: "Mod checksums are calculated when the game starts and are compared with other peers when joining a multiplayer game" (since 0.12.30), to prevent desyncs from locally edited mods. Mods that don't affect game state need no sync (since 0.11.2). — [Factorio wiki Multiplayer](https://wiki.factorio.com/Multiplayer)
- Factorio: deprecated mods stay downloadable on the portal, hidden from search, so that "Sync mods with save" keeps working (FFF #250, July 2018). — (search summary of [factorio.com blog](https://factorio.com/blog/21)). Checksums can differ between identical mod versions when code does conditional `require()` depending on startup settings. — [Factorio forums](https://forums.factorio.com/viewtopic.php?p=270761)
- **Hytale** (post of 2025-11-20 by technical director Slikey): "we don't intend to support any client mods". "You should be able to join any modded Hytale server without downloading external mods or juggling client packs". "The client should remain stable, secure, and consistent, while servers provide the creativity and variation." The team is exploring server-sent client code, with no guarantee. — [Hytale: Modding Strategy and Status](https://hytale.com/news/2025/11/hytale-modding-strategy-and-status). Community docs: the client is C# NativeAOT, a single supported client version, and all mods go through the server API. — [HytaleModding: The Hytale Client](https://hytalemodding.dev/en/docs/established-information/client)
- **Valheim**: no automatic mod download. The client and server must be matched by hand; a mismatch fails with a "mismatch/incompatible" error. r2modman's "Export Profile as Code" is the usual way to share a mod set. Some mods sync config from server to client themselves. — [Supercraft Valheim mods guide](https://supercraft.host/wiki/valheim/install_mods/) (hosting-provider guide, medium reliability)

### Inferences
- GMod FastDL shows what to avoid: no hashes means stale content after updates, and unauthenticated server downloads are a DoS vector. Content hashing fixes the first. Per-peer rate and concurrency limits on the host fix the second.
- Factorio's design is a good analogue for the *semantics* we want: exact versions pinned by the world, startup settings synced together with mods, and a peer checksum comparison as a final consistency check before play. Its weakness is the reliance on a central portal plus an account. We can let the host *be* the source and add catalogs or mirrors as optional extra sources for the same hash.
- Factorio's FFF #250 lesson applies directly: pinned content must stay fetchable. If worlds pin hashes, a host should keep serving every package its world references, and package registries (if we add one) should never hard-delete a hash that worlds reference.
- Hytale and Roblox show the player expectation for 2025–2026: joining a modded world needs no manual install. A consent prompt with size and source is still needed for P2P hosts, since the host is an arbitrary peer rather than a vetted platform.
- Factorio's conditional-require checksum problem warns us to hash **bytes of content**, not anything influenced by settings. Settings belong in the world manifest, separately hashed.

### Gaps
- Factorio: I did not confirm from an official source that the sync downloads from the mod portal and needs a factorio.com login. I believe it does, but it is not cited here. I also did not confirm how mod-portal downloads are integrity-checked.
- Hytale: I found no primary source on the mechanics of asset streaming (hashing, caching, sizes) as of late 2026.
- Roblox: there is no public detail on the client cache format or hash verification.

## 5. Content-addressed transfer: iroh-blobs (BLAKE3/bao), BitTorrent v2, IPFS; SHA-256+custom stream vs BLAKE3+iroh-blobs

### Takeaway
iroh-blobs already provides most of what our plan would build by hand: verified streaming, where every 16 KiB chunk group is checked against the root hash as it arrives; range requests (and therefore resume); collections via HashSeq; multi-provider download; a filesystem store with partial-blob bitfields; tags and GC. It runs on iroh 1.x. Its README still says "not yet considered production quality", it ships a breaking release roughly monthly (0.104.0 on 2026-10-28), and its default `/iroh-bytes/4` ALPN implies a separate QUIC connection. The low-level `provider::handle_stream` does let us serve it over streams on our own connection.

### Cited Findings
- **Versions (crates.io API, queried 2026-10-31)**: iroh 1.0.0 was released 2026-06-15, current is 1.4.1 (2026-10-21). iroh-blobs 0.104.0 came out 2026-10-28, preceded by 0.103.0 (2026-06-15), 0.102.0 (05-27), 0.101.0 (05-08), 0.100.0 (04-20), 0.99.0 (03-17), 0.98.0 (2026-01-28) and 0.96.0 (2025-10-21). Most 0.97–0.103 `.0` releases are **yanked**, with `.1` patch releases all published 2026-10-06. iroh-blobs 0.104.0 depends on `iroh ^1.0.0`, `iroh-base ^1.0.0`, `bao-tree ^0.17`, `irpc ^0.17`, optional `noq ^1.0` and `redb ^4.1`. — [crates.io iroh-blobs](https://crates.io/crates/iroh-blobs); [crates.io iroh](https://crates.io/crates/iroh)
- **Maturity**: "NOTE: this version of iroh-blobs is not yet considered production quality. For now, if you need production quality, use iroh-blobs 0.35". — [iroh-blobs README](https://github.com/n0-computer/iroh-blobs); [docs.rs iroh-blobs 0.104.0](https://docs.rs/iroh-blobs/latest/iroh_blobs/). The 2025 roadmap said blobs would be maintained under its own version numbers, separately from iroh 1.0. — [iroh blog: road to 1.0](https://iroh.computer/blog/road-to-1-0) (search summary)
- **Model**: a request/response protocol based on BLAKE3 verified streaming. "The requester opens a QUIC stream to the provider and sends the request." The request is phrased in hashes plus byte ranges, and the response comes as bao-encoded verified streams on the same stream. Blob = bytes without metadata; Link = 32-byte BLAKE3 hash; HashSeq = blob of concatenated links (size a multiple of 32). — [iroh-blobs README](https://github.com/n0-computer/iroh-blobs)
- **Protocol goals** (source docs): "Be paranoid about data integrity", with validation on both provider and getter. Range-request granularity is "a chunk group of 16KiB or 16 blake3 chunks", with "worst case overhead ... about two chunk groups per range". "Do not limit the size of blobs or collections". Collections exist to avoid per-blob round trips. Non-goals: hash agility, graph traversal, and discovery ("you have to have some out-of-band knowledge about what node has data for a given hash"). Ranges are in 1024-byte BLAKE3 chunks; for example `ChunkRanges::offset(1) | ChunkRanges::last_chunk()` and `ChunkRangesSeq` allow per-child ranges in a HashSeq, which stays efficient "even in case of very fragmented availability of chunks, like a download from multiple providers that was frequently interrupted". On missing or invalid data, or an internal error, the provider closes the connection. `ALPN = b"/iroh-bytes/4"`, `MAX_MESSAGE_SIZE = 1 MiB` for requests. — [iroh-blobs src/protocol.rs](https://github.com/n0-computer/iroh-blobs/blob/main/src/protocol.rs)
- **Integration**: `Router::builder(endpoint).accept(iroh_blobs::ALPN, BlobsProtocol::new(&store, None)).spawn()`, alongside other protocols by ALPN. `BlobTicket` = endpoint address + hash + format. — [README example](https://github.com/n0-computer/iroh-blobs). The low-level provider API exposes `handle_connection(...)`, `handle_stream<R: RecvStream, W: SendStream>(...)`, `handle_get`, `handle_get_many`, `handle_push` and `handle_observe`. An `EventSender` with `ThrottleMode::Intercept` lets the application observe and intercept or throttle requests. — [iroh-blobs src/provider.rs](https://github.com/n0-computer/iroh-blobs/blob/main/src/provider.rs)
- **Downloader**: `api::downloader` "downloads blobs from multiple sources", with `SplitStrategy::{None, Split}` (split a request across providers), a connection pool, and a configurable `alpn(...)`. — [iroh-blobs src/api/downloader.rs](https://github.com/n0-computer/iroh-blobs/blob/main/src/api/downloader.rs); [docs.rs](https://docs.rs/iroh-blobs/latest/iroh_blobs/)
- **Stores**: `MemStore`. The `FsStore` (feature `fs-store`, redb-backed) keeps per-hash data, outboard, sizes and **bitfield** files (the bitfield tracks partial content, which is what makes resume possible), uses a temp dir that must be on the same device for atomic moves, and has inline thresholds for small data. — [iroh-blobs src/store/fs/options.rs](https://github.com/n0-computer/iroh-blobs/blob/main/src/store/fs/options.rs). The API includes `add_path`, `add_bytes`, `export_ranges`, `export_bao`, and `observe`. — [src/api/blobs.rs](https://github.com/n0-computer/iroh-blobs/blob/main/src/api/blobs.rs)
- **bao-tree**: "The merkle tree used for BLAKE3 verified streaming". It is wire-compatible with `bao` but adds runtime-configurable chunk groups and multi-range queries (e.g. `[0..1000, 5000..6000]`), with pre- and post-order outboards. — [bao-tree README](https://github.com/n0-computer/bao-tree). iroh-blobs can compile to WASM with an in-memory store (Feb 2026 post). — (search summary, [iroh blog](https://iroh.computer/blog/road-to-1-0))
- **BitTorrent v2 (BEP 52)**: each file has a "pieces root", which is "the root hash of a merkle tree with a branching factor of 2, constructed from 16KiB blocks of the file" using SHA-256. "Identical files always result in the same root hash", so dedup across torrents is possible. Files are piece-aligned. Hash request/hashes/reject messages (IDs 21/22/23) return the uncle hashes needed to verify individual 16 KiB blocks against the root without downloading whole layers. The infohash is SHA-256 of the bencoded info dict. — [BEP 52](https://www.bittorrent.org/beps/bep_0052.html)
- **IPFS contrast**: "Two identical files can produce different CIDs". "The CID depends on both the content and how that content is structured" (chunk size, DAG layout, codec, CID version, hash). The multihash is the hash of the root block, not of the file bytes, so a CID generally won't equal the file's SHA-256 (exception: a single-block raw leaf). — [IPFS docs: Content addressing](https://docs.ipfs.tech/concepts/content-addressing/)

### Inferences — comparison for our use case

| Property | SHA-256 of zip + custom chunked stream | BLAKE3 + iroh-blobs |
|---|---|---|
| Verify *during* streaming | No. A flat SHA-256 is only known at the end. A malicious or buggy host can make us download all N MB before we detect it. Fixing this means adding per-chunk hashes, i.e. reinventing a merkle tree like BT v2. | Yes. Each 16 KiB group is verified against the root on arrival, and a bad chunk aborts immediately. |
| Resume after disconnect | Custom work: track an offset, trust the partial file, then hash everything at the end. A corrupted partial is only caught at the end. | Built in: range requests plus FsStore bitfields. The verified prefix is kept and the rest requested. |
| Multi-source (any peer in world) | Possible, but without chunk verification you can't attribute a bad chunk to a peer, so one bad peer poisons the whole download. | Downloader with `SplitStrategy::Split`. Per-chunk verification identifies which provider sent garbage. |
| Dedup across packages | Only at whole-zip level. Two packages sharing a 50 MB texture atlas store it twice. | Per blob. If a package is a HashSeq/collection of files, shared files are stored and transferred once. Chunk-level dedup only works for identical whole blobs. |
| Hash identity familiarity | SHA-256 is ubiquitous (Go h1:, BT v2, package managers). | BLAKE3 is less universal, but fast and designed for this. One choice locks you to BLAKE3 for identity. |
| Dependency risk | None (own code). | Pre-production crate, monthly breaking minors, recent mass yank/re-release, an API that changed many times. Pin an exact version. |
| Connection model | Streams on our existing game connection, as planned. | The default is its own ALPN, so a second QUIC connection to the same peer via the same Endpoint (the Router dispatches by ALPN). Alternatively `provider::handle_stream` can serve requests on streams we accept from our own connection. Note that its error path may close the connection; a custom wrapper is needed so a blob error can't kill the game session. |

- **Recommendation**: use **BLAKE3 as the package identity hash** even if we don't adopt iroh-blobs right away. Verified streaming, resume and multi-source are all things we will want, and BLAKE3 + bao gives them with a standard encoding. If we start with SHA-256 we either give up streaming verification or have to bolt on a merkle layer later, and changing the identity hash changes every pinned world manifest. BLAKE3 is the hash iroh-blobs and bao-tree use, so a later switch to iroh-blobs (or to a mirror/peer swarm) needs no change of identity.
- Pragmatic integration: register `iroh_blobs::ALPN` on our existing Router with an FsStore at `cache/packages/` (or use the store's layout instead of our own `<hash>/` directories). The joining client then uses the Downloader with providers = [host] at first, later [host + other players who have the package]. The connection-hello package list carries `(blake3_hash, size, name)`. That stays fully compatible with the "extra streams on the same connection" plan if we wrap `handle_stream` instead of using a separate ALPN. Either way the game connection's ALPN stays separate from blob traffic, which is good for isolation.
- If dependency risk is unacceptable now, the fallback is to use `bao-tree` directly (smaller surface, the merkle/encoding layer only) over our own QUIC streams. That gives verified streaming and range resume with our own request framing. It is still BLAKE3, so a later move to iroh-blobs keeps the same identities.

### Gaps
- I could not open the official iroh blog posts about 1.0 or the iroh-blobs roadmap. There is no confirmed date or plan for iroh-blobs 1.0, and I don't know why the 0.97–0.103 `.0` releases were yanked on 2026-10-06.
- I did not verify how `handle_stream` behaves on error (whether it closes the stream only or the whole connection) when used on a shared application connection. Check this in source before relying on it.

## 6. Hashing a package: archive bytes vs canonical manifest/merkle of files

### Takeaway
Hashing zip bytes is fragile. The same content can produce different zips depending on timestamps, compression level, entry order and tool. Mature systems hash *content*: Go's `h1:` hashes a sorted list of (sha256(file), name) lines, and `HashZip` explicitly ignores encoding, compression and mtimes. BitTorrent v2 hashes per file. Make the package identity a hash of a canonical manifest that lists per-file hashes, i.e. a collection/HashSeq.

### Cited Findings
- Go `dirhash.Hash1` (`h1:`): SHA-256 of each file, then one line per file sorted by name, "the hexadecimal SHA-256 hash of the file content", two spaces, the name; then SHA-256 of that summary, base64-encoded and prefixed with `h1:`. File names containing newlines are disallowed. `HashZip`: "Only the file names and their contents are included in the hash", ignoring "the exact zip file format encoding, compression method, per-file modification times, and other metadata". These hashes go into go.sum and the checksum DB. — [pkg.go.dev dirhash](https://pkg.go.dev/golang.org/x/mod/sumdb/dirhash)
- BT v2 builds the tree per file ("identical files always result in the same root hash") and describes the file layout in a separate file tree inside the info dict, whose SHA-256 is the infohash. — [BEP 52](https://www.bittorrent.org/beps/bep_0052.html)
- IPFS shows the opposite trap: chunking and layout parameters change the identity of identical bytes. — [IPFS docs](https://docs.ipfs.tech/concepts/content-addressing/)
- Minecraft and Luanti hash the transferred artifact directly: the zip for Minecraft, each individual file for Luanti. — [minecraft.wiki Packets](https://minecraft.wiki/w/Java_Edition_protocol/Packets); [Luanti clientmedia.cpp](https://github.com/luanti-org/luanti/blob/master/src/client/clientmedia.cpp)

### Inferences
- **Recommended package format**: package id = BLAKE3 of a canonical manifest blob, e.g. a deterministic encoding (sorted paths, normalized UTF-8 `/` separators, no `..`, no absolute paths, no symlinks) of `[(path, blake3, size)]` plus metadata such as name, version, format version and dependencies by hash. This maps onto iroh-blobs' HashSeq/collection model (one root blob listing child blob hashes). The benefits: per-file dedup across packages and versions (a v1.1 that changes one texture re-downloads one file), on-the-fly verification, and packaging tools don't need to produce byte-identical zips.
- If we keep a single-archive transport for simplicity, hash the archive bytes *as the transfer unit*, but make the authoring tool produce deterministic archives: sorted entries, fixed mtime, fixed compression, no extra fields. Better still, use an uncompressed or tar-like container plus per-file hashes. Zip non-determinism also breaks "two authors build the same package → same hash".
- Never let the identity depend on settings or load order (the Factorio conditional-require lesson). Per-world settings belong in the world manifest, which itself can be hashed and pinned.
- Validate unpacked paths against path traversal and limit file counts and sizes when extracting (§7).

### Gaps
- I found no voxel-game prior art that uses a manifest-of-file-hashes package identity specifically. Go modules, BT v2 and Nix-style systems are the closest analogues; I did not research Nix NAR in this pass.

## 7. Caching, garbage collection, size limits and abuse protection

### Takeaway
The prior art is weak here. Minecraft dropped its 10-pack cache limit and lets the directory grow. Luanti has a per-file 16.7 MB transport cap and seems to never evict. GMod's ServerDL could be spammed to lag servers. iroh-blobs deliberately sets no size limits, but provides tags, temp tags and GC with a "protect" callback. Size caps, consent thresholds and eviction policy are ours to design.

### Cited Findings
- Minecraft 1.20.3+: downloaded server packs "are no longer automatically cleaned (previously only up 10 packs were kept)". Pack size limit is 250 MiB. — [minecraft.net 1.20.3-pre1 (search summary)](https://minecraft.net/en-us/article/minecraft-1-20-3-pre-release-1); [minecraft.wiki Server.properties](https://minecraft.wiki/w/Server.properties)
- Luanti: `MEDIAFILE_MAX_SIZE` is 16,700,000 bytes per file. The cache only adds files and re-verifies on load. — [networkprotocol.h](https://github.com/luanti-org/luanti/blob/master/src/network/networkprotocol.h); [clientmedia.cpp](https://github.com/luanti-org/luanti/blob/master/src/client/clientmedia.cpp)
- GMod: ServerDL is capped at 64 kB/s, and modified clients can spam file requests to lag the server. WorkshopDL is about 2 GB. There is an 8192-file limit across `resource.Add*`. — [GMod Serving Content](https://wiki.facepunch.com/gmod/Serving_Content); [resource.AddWorkshop](https://wiki.facepunch.com/gmod/resource.AddWorkshop)
- iroh-blobs: "Do not limit the size of blobs or collections" is a protocol goal, while request messages are capped at 1 MiB. — [protocol.rs](https://github.com/n0-computer/iroh-blobs/blob/main/src/protocol.rs). `GcConfig { interval, add_protected: Option<ProtectCb> }`: the callback fills a `HashSet<Hash>` of protected hashes before each run and can return `ProtectOutcome::Abort` to skip GC when the protect source failed. Long writes are protected via `Batch::temp_tag`. A Tags API (`set`, `list`, `list_prefix`, `delete`, `list_temp_tags`, `list_hash_seq`) keeps roots alive. — [iroh-blobs src/store/gc.rs](https://github.com/n0-computer/iroh-blobs/blob/main/src/store/gc.rs); [src/api/tags.rs](https://github.com/n0-computer/iroh-blobs/blob/main/src/api/tags.rs)
- The provider-side `EventSender` / `ThrottleMode::Intercept` gives a hook to authorize or throttle requests per connection. — [provider.rs](https://github.com/n0-computer/iroh-blobs/blob/main/src/provider.rs)
- Clients choosing which file types to download (GMod) and accepting or declining per pack (Minecraft) are established consent patterns. — [GMod Serving Content](https://wiki.facepunch.com/gmod/Serving_Content); [minecraft.wiki Resource pack](https://minecraft.wiki/w/Resource_pack)

### Inferences — concrete policy recommendations
- **The declared size is part of the commitment.** The hello lists `(hash, size)` per package and per file. The client refuses anything over its limits *before* downloading and aborts the moment received bytes exceed the declared size. With BLAKE3/bao the size is bound to the hash: the tree shape depends on length, and iroh-blobs lets you fetch the last chunk to obtain a verified size cheaply. A lying host is therefore caught after at most one chunk group.
- **Limits** (suggested defaults, configurable): max total download per join without an extra prompt (e.g. 100 MB → show size in the consent dialog; above e.g. 1 GB → a stronger warning); max per-package size; max files per package (cf. GMod's 8192); max manifest blob size; max path length and depth; and a decompression-ratio limit if any compression is used (zip-bomb defense). Pick a cap like Minecraft's 250 MiB per package, or a total budget per world.
- **Consent UX**: "World 'X' needs 3 packages (212 MB) you don't have, from host <name/id>. [Download & join] [Leave]". Show already-cached packages as free. Treat packages with code (scripts or WASM, if we ever allow them) as needing an explicit, separate trust decision; Hytale and Luanti CSM both treat client code as a security boundary.
- **Host-side abuse protection**: serve only hashes referenced by the current world manifest (not arbitrary store contents; use the intercept hook or a custom handler). Set per-peer concurrent stream limits and bandwidth shaping so downloads don't starve game traffic on the same path (QUIC stream priorities, or a separate connection for blobs). Only serve to authenticated session peers (the iroh NodeId was already accepted for the session).
- **Cache layout and GC**: content-addressed store at `cache/packages/` with write-to-temp, verify, then atomic rename (iroh-blobs FsStore does this; a custom store should copy it). Never use a partially verified package; keep partials only as resumable state. Maintain a "pins" index: package hashes referenced by worlds on disk and recently joined servers, plus their last-used timestamps. Run GC with LRU eviction under a configurable budget (e.g. 2–5 GB), never evicting pinned hashes. With iroh-blobs this is `Tags` per world plus `GcConfig::add_protected` driven by the world index, with Abort when the index can't be read. Re-verify on load the way Luanti does, or at least verify at first use per session; BLAKE3 is fast enough.
- **Retention for pinned worlds**: a host must keep every package its world pins. Add a "missing package" error path for when the host itself lacks one, and allow alternative sources by hash (other players in the world, a mirror URL serving files by hash like Luanti's remote_media).

### Gaps
- I found no published numbers for typical mod-pack sizes in voxel games on which to base default limits. The numbers above are suggestions, not sourced norms.

## 8. Synthesis: how the tentative plan should change

### Takeaway
The plan is sound and matches the best prior art (Luanti's hash-keyed cache with only-misses fetch; Minecraft's configuration phase with a known-packs-style negotiation). Five changes: (1) use BLAKE3 instead of SHA-256 for identity; (2) make a package a manifest of per-file hashes rather than a zip hash; (3) add an explicit configuration phase with have/need negotiation, atomic validation and an ack, re-enterable from play; (4) use verified streaming (iroh-blobs, or bao-tree directly) so resume and multi-source come for free; (5) define limits, consent and GC up front.

### Cited Findings
- Verified streaming, ranges, multi-provider download, stores and GC exist in iroh-blobs 0.104 on iroh 1.x. It is flagged non-production. — [iroh-blobs README](https://github.com/n0-computer/iroh-blobs); [crates.io](https://crates.io/crates/iroh-blobs)
- Hash-keyed cache, verify on receive and load, fetch only misses, and by-hash mirrors with fallback are proven in Luanti. — [clientmedia.cpp](https://github.com/luanti-org/luanti/blob/master/src/client/clientmedia.cpp); [Luanti remote media](https://docs.luanti.org/for-server-hosts/remote-media/)
- Have/need negotiation plus authoritative registry listing plus atomic validate-then-ack is Minecraft's configuration and known-packs design. — [minecraft.wiki Packets](https://minecraft.wiki/w/Java_Edition_protocol/Packets)
- Content-based (not archive-byte) package hashing is Go's dirhash. — [pkg.go.dev dirhash](https://pkg.go.dev/golang.org/x/mod/sumdb/dirhash)

### Inferences
- **Proposed flow**: 1) The hello includes `world_manifest_hash` and `[(pkg_root_blake3, total_size, display_name, kind{assets|data|code})]`. 2) The client checks the cache and replies `Have[...]`, `Need[...]`, `Declined[...]` (cf. Serverbound Known Packs). It shows the consent dialog if Need exceeds its threshold. 3) Downloads run per package root (a HashSeq/collection) over blob streams, verified per chunk, written into the CAS store, with per-package status events reported to the host (cf. Minecraft's Result enum). 4) The client validates the full set (all roots present, manifests parse, dependency hashes satisfied), then loads them. 5) The host sends the session registry/ID map (authoritative, cf. Registry Data). 6) The client acks and enters play. Play → configuration re-entry handles hot package changes.
- **Dependency decision**: if iroh-blobs' churn is acceptable (pin `=0.104.0`, budget for upgrades), adopt it for the store and protocol now. Otherwise, implement framing over our own streams with `bao-tree` for encoding and verification, keeping BLAKE3 identities so we can migrate later. Either path is better than flat SHA-256 plus a custom chunked stream, which verifies only at the end, makes resume unsafe, and cannot do multi-source with blame.
- Keep `cache/packages/<hash>/` as the *extracted, verified* view if the engine wants loose files. Treat it as derived from the CAS store, so it can be rebuilt and is GC'd alongside it.

### Gaps
- None beyond those listed in sections 1–7.
